# Правила анализа, версия 1.0

Все роли — гипотезы для проверки. `role_score` — эвристическая выраженность
правила с поправкой на конкуренцию; это не вероятность нарушения.
Данных для измерения accuracy нет. Числа в config.toml не зависят от gid.

## Признаки и пороги

Основа порогов — распределения в DATA_PROFILE.md. Число плательщиков 3 и
получателей 5 соответствует p95 по всему графу; минимальный оборот 164 528 ₸
соответствует p75 входящего объёма. Betweenness 0,0001553 — округлённый p95,
охват 9 seed — p90, число внешних соседних кластеров 2 — p95.
Доля выхода с недавним входом 0,69 — округлённый p90 по всем узлам.

Остальные границы — интерпретируемые ограничения, а не обученные пороги:
концентрация ≤0,8 не даёт одному контрагенту полностью объяснять веер/сбор;
охват минимум 2 означает несколько ветвей seed. Транзит требует близких
объёмов (0,7–1,4; около наблюдаемой медианы 1,065 у не-seed с входом и выходом).
Удержание требует выхода ≤10% входа — около p10=0,105 в той же подвыборке.
Эти границы нуждаются в ручной проверке и не являются банковскими нормативами.

| Роль | Все обязательные условия |
|---|---|
| consolidator | ≥3 плательщиков, ≥2 достижимых seed, максимальная доля одного входящего контрагента ≤0,8 |
| distributor | ≥5 получателей, максимальная доля одного исходящего контрагента ≤0,8 |
| transit | не seed, есть вход и выход к другим узлам, каждый объём ≥164 528 ₸, out/in от 0,7 до 1,4, доля близости дат ≥0,69 |
| terminal | не seed, не обрыв depth=4, есть вход от другого узла ≥164 528 ₸, out/in ≤0,1 |
| coordinator | ≥9 достижимых seed, ≥2 внешних соседних кластеров, направленная невзвешенная betweenness ≥0,0001553 |
| peripheral | ни одно из перечисленных правил не сработало |

Для допустимых правил вычисляется score:

- consolidator: `0,6 + 0,2 min(in_deg / 6, 1) + 0,2 (1 − in_concentration)`;
- distributor: `0,6 + 0,2 min(out_deg / 10, 1) + 0,2 (1 − out_concentration)`;
- transit: `0,6 + 0,2 min(ratio, 1/ratio) + 0,2 timing_share`;
- terminal: `0,6 + 0,2 (1 − ratio) + 0,2 min(in_kzt / 329056, 1)`;
- coordinator: `0,6 + 0,2 min(betweenness / 0,0003106, 1) + 0,2 min(neighbor_cluster_count / 4, 1)`.

Числа в знаменателях равны удвоенным соответствующим порогам config.
Берётся наибольший допустимый score. При равенстве — порядок `role_order`
в config: coordinator, consolidator, distributor, transit, terminal, peripheral.
Итоговый role_score умножается на `(1 − 0,2 × лучший альтернативный score)`.
У peripheral фиксированное 0,25: это слабая определённость при отсутствии
оснований, а не уверенность в безвредности. Все исходные скоры доступны в
`role_scores`, факты — в признаках и evidence. Значения недопустимых ролей равны 0.

## Приоритет

Приоритет не зависит от выбора одной роли и не равен role_score:

`0,35 N(seed_reach) + 0,40 [N(betweenness)+N(in_deg+out_deg)]/2 + 0,25 N(in_kzt+out_kzt)`.

`N(x)=log(1+x)/max(log(1+x))` по всем узлам текущего запуска. При нулевом
максимуме N=0; у постоянного положительного признака N=1 для всех — он не
различает узлы. Веса выражают предпочтение структурного охвата (75%) перед
объёмом (25%); они не оптимизированы на отсутствующей разметке.
Вклады сохранены отдельно. Равенства приоритета разрешаются по числовому gid.
Топ содержит все узлы с последовательными rank от 1, что превышает минимум 20.

## Граф, даты и кластеры

Все 2 248 узлов входят в граф. PageRank взвешен по sum_kzt; ошибка сходимости
прерывает расчёт. Betweenness направленная, без весов длины. Достижимость от
каждого seed считается отдельно; узел не считается достижимым от самого себя.
Самопереводы входят в оборот, но не в число разных контрагентов и не во
временной признак. Неопределённые отношения в JSON равны null.

Для каждой исходящей даты суммируется объём, если есть вход в тот же день
или за два предшествующих дня; каждый исходящий объём учитывается один раз.
Это близость дат, не сопоставление денег. Внутридневной порядок неизвестен.
Повторы транзакций сохранены.

Louvain работает на ненаправленной проекции с суммой встречных потоков,
без петель. Seed=42, resolution=1; порядок добавления узлов/рёбер фиксирован.
Изоляты получают отдельные кластеры. Номера кластеров идут по минимальному
числовому gid. Выбор resolution=1 — исходный масштаб модульности, не подбор
под число сообществ из примечания организаторов. Получено 88 кластеров.
`top_gids` — до 5 лидеров по приоритету, в CSV JSON-массив десятичных строк.
Внутренний оборот включает петли и каждое направленное ребро один раз.

## Проверка устойчивости и текущий результат

На исходных данных: peripheral 1751, terminal 282, distributor 119,
consolidator 72, transit 19, coordinator 5. Полный расчёт Parquet → четыре
файла занял 1,979 с в локальном окружении; это ещё не замер в Docker.
Повторный расчёт даёт побайтово одинаковые CSV и JSON.

Совместное изменение на ±10% порогов числа плательщиков/получателей,
объёма, охвата coordinator, числа внешних кластеров и betweenness:

| Изменение | Смена роли | Доля |
|---|---:|---:|
| −10% | 27 / 2248 | 1,20% |
| +10% | 83 / 2248 | 3,69% |

При +10% coordinator исчезает: все пять кандидатов чувствительны к границам.
Это существенная неопределённость роли, а не свидетельство устойчивой
организаторской функции. Приоритет при таком изменении не меняется,
поскольку использует непрерывные признаки. Это локальная проверка
чувствительности, не доказательство качества модели.

Ограничения выборки (seed, depth=4, июль, внутрибанковские операции и порог
5000 ₸) сохраняются в meta, data_warnings и кратких объяснениях. Термин
terminal означает наблюдаемое удержание внутри выборки. Ни одна роль
не подтверждает преступление. Следующий шаг аналитика — запрос полных
входящих seed, продолжения depth=4 и операций за соседние периоды.
