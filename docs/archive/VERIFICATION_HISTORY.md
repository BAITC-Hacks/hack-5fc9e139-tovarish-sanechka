## Чистая копия и контейнер

Актуальные файлы репозитория скопированы в новый временный каталог;
локальные `.venv`, `node_modules`, `dist`, `out` и `.git` отсутствовали.
UI и Python-зависимости устанавливались только внутри build-стадий.
`docker compose config --quiet` и затем
`docker compose up -d --build --wait --wait-timeout 360` завершились успешно,
сервис app — healthy. Чтобы не занимать уже работающий 8080, только host-порт
в копии `compose.yaml` заменён на 8082; контейнерный порт и Dockerfile не
менялись. Основной сервис на 127.0.0.1:8080 пересобран из актуального
репозитория и также стал healthy; новый поиск прошёл E2E-проверку на нём.

Первый пробный образ выявил закрытые права каталогов из исходной копии;
Dockerfile исправлен (`a+rX`), итоговый образ проверен от uid 10001.
Исходные Parquet репозитория не менялись.

Ранее на выделенном тестовом проекте проверены механизмы отказа и восстановления;
после расширения аналитики эти сценарии повторно не запускались:

1. Restart → новый run_id, идентичные хеши результатов, healthy.
2. Второй `python run.py` в обслуживаемый каталог → явный отказ блокировки.
3. Дописан байт в CSV внутри контейнера → healthcheck завершился с ошибкой.
4. Restart → результаты восстановлены пересчётом, healthy.
5. Удалён nodes.parquet только внутри тестового контейнера, затем restart →
   exit code 1; старые HTTP-результаты недоступны.
6. `up --force-recreate --wait` → данные из образа восстановлены, healthy.
7. Расчёт с `docker run --network none` → успешно без внешних подключений.
8. SIGTERM при restart корректно завершает HTTP-сервер.

Healthcheck сверяет по HTTP index, assets, analysis.json и три CSV с хешами
полностью проверенного текущего запуска; дополнительно проверяет схемы и
число строк. В текущей сборке `docker compose exec -T app python healthcheck.py`
завершился успешно. Хеши контейнерных CSV из чистой копии и основного сервиса
