# План решения кейса «Граф денег»

Статус: прочитаны PDF с ТЗ, оба README и стартовый код. Реализация решения
ещё не начата. Числа ниже взяты из материалов организаторов; содержимое
Parquet пока не проверено вычислениями.

## Цель и обязательный результат

Помочь AML-аналитику ответить: кого проверять первым и почему.
Роли и связи — гипотезы для проверки, а не утверждения о виновности.

Вход: 2 248 узлов, 3 119 направленных рёбер, 4 840 транзакций за июль 2026.
Один локальный запуск должен за время менее пяти минут создавать:

- `nodes_roles.csv`: все 2 248 уникальных `gid`, включая изолированные;
  `role`, `role_score`, `cluster_id`, `priority_score`, `evidence`.
  Скоры в диапазоне 0–1; объяснение с числами, не длиннее 200 символов.
- `clusters.csv`: `cluster_id`, `n_nodes`, `n_seed`, `sum_kzt_internal`,
  `top_gids`, `hypothesis`.
- `top_nodes.csv`: минимум 20 узлов, `rank`, `gid`, `role`,
  `priority_score`, `why`, сортировка по убыванию приоритета.
- Экран сети: направление переводов, роли, кластеры, поиск по `gid`,
  просмотр связей и объяснения выбранного узла.

Дополнительно для сдачи: README с одной командой запуска, критериями ролей
и порогами, ограничениями и подходом к масштабу около миллиона узлов;
диаграмма решения и пятиминутное демо с разбором 2–3 узлов.

Обязательный способ поставки — Docker Compose: из свежей копии репозитория
`docker compose up -d --build` собирает UI, подготавливает Python-окружение
и запускает расчёт автоматически. После готовности открыть
`http://localhost:8080`. На хосте нужны только Docker с Compose v2 и браузер.
Для ожидания готовности добавить `--wait --wait-timeout 360`.
Детали контейнеризации и проверки описаны в `TECH_HANDOFF.md`.

## Подход

Развивать `case/starter/starter.py`, сохранив существующую загрузку и схемы
выгрузок. Сначала получить объяснимый результат на правилах и графовых
метриках. Размеченных ролей нет: accuracy здесь измерять не по чему.
Не требовать внешних данных, платных сервисов или GPU.

1. **Проверить данные.** Схемы, пропуски, уникальность `gid` и пар рёбер,
   наличие концов рёбер в nodes, даты, суммы и количества транзакций.
   Сверить агрегацию transactions с edges по парам, суммам с числовым
   допуском и точным `n_tx`. В текущем `sanity_check` проверяются только пары.
   Повторы транзакций не удалять автоматически: одинаковые поля могут
   соответствовать реальным отдельным переводам.
2. **Построить полный граф.** Добавить все nodes, затем направленные рёбра
   с весами суммы и количества. Сейчас `build_graph` добавляет только
   участников рёбер. По ТЗ 19 seed изолированы; их нельзя потерять.
   Различать компоненты графа рёбер и полного графа с изолятами.
3. **Посчитать признаки.** Число контрагентов, суммы и количество
   входящих/исходящих переводов, концентрацию потоков, PageRank,
   достижимость от разных seed. Добавить дневную активность и признаки
   возможного транзита за 1–2 дня. Даты не дают порядок операций внутри дня
   и не доказывают перемещение именно тех же денег.
4. **Назначить роли.** Задать формальные правила, явный порядок разрешения
   конфликтов и объяснения из тех же признаков, что определили роль.
   Пороги выбрать после просмотра распределений и документировать;
   конкретные `gid` в правила не зашивать.
5. **Выделить кластеры.** Начать с компонент и сообществ внутри них.
   Для ненаправленной проекции явно суммировать веса встречных рёбер;
   направление сохранить для анализа ролей и отображения потоков.
   Зафиксировать random seed и стабильную нумерацию кластеров.
   Изолятам также назначить кластер. Гипотезы подкреплять агрегатами.
6. **Ранжировать.** Отделить уверенность в роли от приоритета проверки.
   Приоритет сочетает выраженность структурной роли, охват seed и объём
   наблюдаемых потоков. Документировать нормализацию и веса, показать
   вклад признаков. Неполнота данных должна быть видна в объяснении.
7. **Показать результат.** Топ-лист → карточка узла → его окружение на
   направленном графе. Поиск по всем `gid`, включая изоляты; фильтры ролей
   и кластеров. Выбор технологии интерфейса оставить до готовности
   аналитических выгрузок; обеспечить локальную работу без CDN.
8. **Проверить сдачу.** Все обязательные поля, диапазоны, словарь ролей,
   длину evidence, согласованность кластеров и топ-листа, повторяемость
   запуска и время выполнения. Проверить сценарий поиска и просмотра
   связей в браузере через Playwright, если выбран веб-интерфейс.

## Рабочие гипотезы ролей

| Роль | Основание для правила |
|---|---|
| `consolidator` | Сбор от нескольких независимых плательщиков и ветвей seed; концентрация входящего потока |
| `transit` | Значимые входящие и исходящие, сопоставимые объёмы и временная близость переводов |
| `distributor` | Много получателей и выраженное распределение исходящего потока |
| `terminal` | Наблюдаемое удержание внутри выборки при отсутствии признака обрыва обхода |
| `coordinator` | Связь нескольких ветвей или сообществ, охват seed и структурная значимость; одного PageRank недостаточно |
| `peripheral` | Недостаточно признаков остальных ролей; объяснять малую активность или недостаточность наблюдений |

`role_score` — эвристическая уверенность, а не откалиброванная вероятность.
При конкурирующих ролях сохранять признаки альтернатив и понижать уверенность.

## Ограничения, влияющие на правила

- 444 узла на depth=4 не имеют исходящих из-за границы выгрузки.
  Не назначать им `terminal` только из-за `out_deg=0`; сохранять
  `truncated_by_depth` и явно указывать неопределённость. По этим данным
  достоверно восстановить их дальнейшие переводы невозможно.
- Входящие seed неполны, но и для остальных узлов баланс не является
  полным банковским балансом. `out_kzt / in_kzt` не трактовать как
  доказательство аномалии; нулевой вход не заменять выдуманным значением.
- Нет межбанковских переводов, операций меньше 5 000 KZT и данных за
  пределами июля. Даже `terminal` внутри границы — только гипотеза.
- По ТЗ 31 seed не имеет исходящих, в том числе 19 вообще нет в рёбрах.
- Суммы переводов по последовательным рёбрам повторно учитывают оборот;
  сумма по графу не равна объёму уникальных денег.
- Отсутствие ground truth требует ручного разбора примеров и проверки
  устойчивости правил при небольших изменениях порогов.

## Порядок работ на пять часов

| Время | Результат |
|---|---|
| 0:00–0:40 | Проверенные данные, полный граф, распределения признаков |
| 0:40–1:50 | Базовые правила всех ролей, объяснения, кластеры и приоритеты |
| 1:50–2:30 | Три заполненных CSV и проверки контракта |
| 2:30–3:40 | Экран поиска, топ-листа и окружения узла |
| 3:40–4:20 | Временные признаки и проверка пограничных случаев |
| 4:20–5:00 | Проверка Compose из свежей копии, замер времени, README, диаграмма и демо |

Если времени мало, сначала закрыть обязательные результаты. Циклы,
симуляцию удаления узлов, ML-аномалии и LLM-ассистента оставить на потом.
Для миллиона узлов описать пакетную агрегацию, более компактное хранение
графа, приближённые метрики и отображение локальных подграфов; сейчас
такую инфраструктуру не строить.
