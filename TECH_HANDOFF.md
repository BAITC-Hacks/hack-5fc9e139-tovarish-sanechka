# Технический план для агента реализации

Статус: рекомендуемые решения для MVP, а не описание уже написанного кода.
Продуктовые требования и ограничения см. в PDF кейса и `PLAN.md`.
Стартовый код ещё не запускался; Parquet ещё не профилировались.

## 1. Стек и границы

| Слой | Выбор | Назначение |
|---|---|---|
| Runtime | Python 3.12, uv, pyproject.toml + uv.lock | Воспроизводимое окружение аналитики |
| Поставка и запуск | Docker + Docker Compose v2 | Сборка и запуск проекта одной командой |
| Данные | pandas, PyArrow, NumPy | Чтение Parquet, агрегации и признаки |
| Граф | NetworkX + SciPy | Направленный граф, PageRank, компоненты и Louvain |
| Frontend | React + TypeScript + Vite | Одна локальная страница анализа |
| Визуализация | Cytoscape.js напрямую | Узлы, направленные рёбра, выбор и окружение |
| UI | Обычный CSS, native controls и таблица | Минимум зависимостей на первом экране |
| Проверки | pytest, TypeScript, Playwright | Аналитические инварианты, сборка, основной сценарий |

Python 3.12 — выбранная целевая версия, не требование кейса. Для сборки UI
использовать совместимую с выбранным Vite поддерживаемую Node.js LTS.
При реализации зафиксировать фактически проверенные версии Python/Node
и зависимости в lock-файлах; сейчас их совместимость не проверена.
SciPy добавить явно: существующий `nx.pagerank` зависит от него.

Архитектура: локальный batch-пайплайн → три CSV + `analysis.json` → статический
UI. В контейнере HTTP-сервер слушает `0.0.0.0:8080`; Compose публикует
`127.0.0.1:8080:8080`. Сервер обслуживает только каталог результата.
Расчёты в браузере не дублируются. Docker Compose — обязательный основной
способ запуска. API, БД, Redis, очередь задач, авторизация и LLM для MVP не нужны.

Причина выбора: вход фиксирован, пересчёт пакетный, всего 2 248 узлов.
FastAPI имеет смысл добавлять при появлении загрузки нескольких датасетов,
пересчёта из UI или сохранения пользовательской работы. Сейчас таких требований нет.
Более быстрый по разработке запасной вариант — Streamlit; основной вариант
React удобнее для согласования выбора в таблице, карточке и графе.

## 2. Размещение кода

Сохранить `case/data/` и PDF как исходные материалы. Развивать существующие
функции `load`, `sanity_check`, `build_graph`, `basic_features`, `write_outputs`
в `case/starter/starter.py`. Не создавать второй независимый пайплайн.

Предлагаемые новые файлы, создавать только по мере необходимости:

```text
pyproject.toml, uv.lock       зависимости и dev-проверки
Dockerfile                   multi-stage сборка UI и Python runtime
compose.yaml                 один сервис app, порт 8080, healthcheck
.dockerignore                исключения для контекста сборки
config.toml                  пороги, веса, random_seed, версия правил
run.py                       запуск расчёта, сборка каталога результата, serve
case/starter/starter.py      существующий CLI и аналитика
web/package.json             frontend-зависимости и scripts
web/package-lock.json        фиксированное frontend-окружение
web/src/types.ts             контракт analysis.json
web/src/App.tsx              загрузка и состояние выбора/фильтров
web/src/GraphView.tsx         жизненный цикл Cytoscape
web/src/NodeTable.tsx         таблица с сортировкой и пагинацией
web/src/NodeDetails.tsx       карточка и доказательства
tests/                       только значимые аналитические проверки
web/e2e/                     основной пользовательский сценарий
out/                         CSV, analysis.json, собранные assets
```

Не раскладывать каждую функцию в отдельный модуль. Выделить `features.py`
или `scoring.py` рядом со starter только при реальном росте сложности.
Корневой README дополнить запуском; README организаторов не заменять.
Если starter/requirements.txt остаётся поддерживаемым способом установки,
согласовать его с основным окружением и добавить SciPy.

## 3. Контракт аналитики и интерфейса

Один запуск строит один набор результатов. CSV и JSON формируются из одних
и тех же таблиц, а не рассчитываются отдельными ветками.

`analysis.json`, версия контракта `1`:

- `schema_version`: число.
- `meta`: период, количество узлов/рёбер/транзакций, версия правил,
  использованные пороги и веса, ограничения выборки.
- `nodes`: все узлы с полями обязательного CSV, дополнительными признаками
  и объяснением. `gid` здесь **строка**, в Python и CSV — int64.
- `edges`: `id`, `src`, `dst`, `sum_kzt`, `n_tx`, `depth`.
  `src`/`dst` — строки; `id` детерминированный, например `edge:src:dst`.
- `clusters`: данные clusters.csv; `top_gids` в JSON — массив строк.
- `top_nodes`: данные top_nodes.csv; `gid` — строка.

Обязательные CSV-поля и типы сохранить из ТЗ. `top_gids` в CSV кодировать
документированно, например строкой с JSON-массивом десятичных строк gid.
JSON содержит только конечные числа; неопределённый дополнительный признак
(`pass_through` при нулевом входе) — `null`. У обязательных CSV-полей
пропуски запрещены. Не превращать неизвестное отношение в ноль.

Дополнительные признаки узла: `in_deg`, `out_deg`, `in_kzt`, `out_kzt`,
`in_tx`, `out_tx`, `pagerank`, `pass_through`, `depth`, `is_seed`,
`truncated_by_depth`, `reachable_seed_count`, `data_warnings`.
Признаки, реально используемые правилами, экспортировать для разбора роли.
`data_warnings` в JSON — массив стабильных кодов, UI переводит их на русский.

Frontend хранит выбранный `gid`, фильтры и режим графа. После загрузки
проверяет schema_version, наличие необходимых полей и уникальность ID.
Не пересчитывает role_score/priority_score. Поиск ведётся по всем узлам,
даже если текущий фильтр или отображаемый подграф их скрывает.

## 4. Аналитическая реализация

Порядок: валидация → полный DiGraph → признаки → кластеры → роли → приоритет
→ объяснения → проверка выходных данных → публикация файлов.

- Сначала добавить все nodes, затем edges. Проверить суммы и количество
  после группировки транзакций, не только наличие пар. Ошибки валидации
  возвращают ненулевой exit code с причиной; рабочие проверки не делать
  через `assert`, который отключается при оптимизированном запуске Python.
- Для охвата seed обходить исходящие связи отдельно от каждого seed,
  с visited; считать разные достижимые seed, исключая сам узел из счёта.
  Это топологическая достижимость, а не доказанное происхождение денег.
- PageRank взвесить по `sum_kzt`. Отказ сходимости сообщать явно.
  Не превращать ошибку алгоритма в фиктивные нулевые оценки.
- Louvain считать на явно построенной ненаправленной проекции: сумма
  встречных потоков даёт вес пары. Изоляты — отдельные кластеры.
  Самопереводы учитывать в оборотах, но исключить из проекции кластеризации;
  в степенях разных контрагентов себя не считать. Эти различия описать.
- Зафиксировать seed, порядок добавления узлов/рёбер и параметр resolution.
  Кластеры нумеровать по отсортированному минимальному gid каждого кластера.
- Не использовать `sum_kzt` как длину пути для betweenness: это сделает
  большие потоки «дальними». Для MVP достаточно невзвешенной направленной
  betweenness, если она нужна coordinator и укладывается в замер времени.
- Правила выдаются как score для каждой роли + числовые основания.
  Выбрать максимальный допустимый score; порядок разрешения равенств
  зафиксировать в config. При недостатке оснований — peripheral.
- Для depth=4 без исходящих запретить вывод terminal на основании
  удержания. Для seed отключить балансовое правило transit/terminal.
  Для остальных ratio тоже считать только наблюдаемым признаком.
- Дневные признаки считать по `transactions`, сохраняя повторы операций.
  Временное совпадение входа и выхода не называть трассировкой тех же денег.
- Пороги и веса выбрать после профилирования, сохранить в config и README.
  Не брать числа из примечания организаторов как готовые границы классов.
- Разделить role_score и priority_score. Определить нормализацию каждого
  слагаемого и поведение на постоянном/нулевом признаке. Начать с комбинации
  охвата seed, структурной значимости и оборота, а не только суммы денег.
- Объяснения генерировать шаблонами из сработавших правил. Короткий evidence
  строить в пределах 200 символов без обрезания существенных оговорок.
- При равном приоритете сортировать по gid; rank начинается с 1.
- Записывать результат только после полной валидации. Не смешивать CSV
  прошлого запуска с JSON нового. Для MVP запретить конкурентные запуски
  в один output-каталог и не обслуживать его во время пересчёта.

Пока открыты только аналитические решения: конкретные пороги, веса и
разрешение Louvain. Агент выбирает их по данным, показывает распределения
и разбирает примеры; пользователь не должен назначать их наугад.

## 5. Технические требования UI

Новый локальный ops-инструмент для аналитика. Сценарий: приоритетный список
или поиск gid → карточка → окружение. Первая задача — выбрать узел для
проверки. Приоритет информации: объяснение, наблюдаемые потоки, связи,
неполнота данных. Референсы структуры: Carbon и PatternFly data tables.

Реализовать компактную таблицу, панель графа и карточку; русский интерфейс.
Состояния: загрузка, ошибка с повтором, gid не найден, нет совпадений фильтра,
изолированный узел. На узком экране сохранить поиск и карточку доступными.
Пользовательские подсказки должны описывать данные, а не архитектуру приложения.

Граф по умолчанию показывает выбранный узел и его окружение на один шаг;
отдельный режим — кластер. Таблица охватывает весь датасет.
Стрелки показывают направление, цвет — роль, легенда расшифровывает роли.
При ограничении числа видимых элементов показать сколько скрыто и способ
расширить просмотр. Не выдавать обрезанный UI-подграф за полный граф данных.

Cytoscape подключить без React-wrapper: создание в effect, хранение instance
в ref, уничтожение при unmount, корректное снятие обработчиков и resize.
Не запускать раскладку заново при каждом выборе строки. Layout только для
отображаемого подграфа; координаты не участвуют в аналитических признаках.
Таблица и карточка должны давать доступ к фактам без обязательного клика
мышью по canvas. Состояния ролей различать также текстом, а не только цветом.

Vite собирает JS/CSS локально; не использовать CDN, удалённые шрифты и
внешние runtime API. Загрузка analysis.json и скачивание CSV — с того же origin.
SSR, router, Redux и TanStack Query для одной страницы пока не нужны.
При усложнении таблицы можно добавить TanStack Table вместо самописного движка.

## 6. Запуск и проверка

Основной критерий воспроизводимости: свежая копия репозитория, установленный
Docker с Compose v2 и браузер. На хосте не нужны Python, Node.js, uv,
ручной pip/npm install, предварительные CSV или обязательный .env.
Целевой сценарий — агент должен его реализовать, сейчас он не работает:

```sh
docker compose up -d --build
firefox http://localhost:8080
```

Firefox — пример; подойдёт любой современный браузер. `-d` возвращает
управление до готовности расчёта. Для сценария «команда завершилась — сразу
открываем готовое приложение» использовать ожидание healthcheck:

```sh
docker compose up -d --build --wait --wait-timeout 360 && firefox http://localhost:8080
```

Требования к реализации Docker:

- Один сервис `app`. Multi-stage Dockerfile: Node-стадия выполняет `npm ci`
  и production build; Python-стадия устанавливает зависимости из uv.lock
  в locked-режиме. Финальный образ содержит Python-окружение, код, config,
  исходные Parquet и готовую сборку UI. Node.js в runtime не нужен.
- Зафиксировать проверенные версии базовых образов и uv, а для базовых
  образов также digest; не использовать `latest`. Lock-файлы обязательны.
- При каждом старте контейнер сам рассчитывает результаты из Parquet,
  валидирует их и только затем запускает HTTP-сервер. Не требовать
  `docker compose exec`, отдельной команды расчёта или локальной сборки UI.
- Встроенные данные и config копируются при build. После их изменения
  повторный `up -d --build` должен включить новые входные файлы в образ.
  Достаточно writable-каталога результатов внутри контейнера, без
  обязательных bind mounts и зависимости от прав пользователя на хосте.
- Сервер запускается от непривилегированного пользователя, с корректной
  обработкой SIGTERM. Ошибка расчёта завершает контейнер с ненулевым кодом;
  не скрывать её бесконечными автоматическими рестартами.
- Healthcheck проверяет HTTP-доступность index.html, валидного analysis.json
  и трёх CSV текущего запуска. Использовать Python stdlib, чтобы не
  зависеть от отсутствующего curl. Дать стартовому расчёту до пяти минут;
  статус healthy возможен только после его успешного завершения.
- CSV доступны для скачивания в интерфейсе. Пересоздание контейнера
  пересчитывает результаты; исходные файлы в репозитории не изменяются.
- `.dockerignore` исключает `.git`, `.serena`, локальные окружения,
  node_modules, старые out/dist, кэши, секреты и macOS-метаданные.
  Не исключать lock-файлы и входные Parquet.
- Первая сборка может требовать интернет для образов и пакетов. После
  сборки запуск, расчёт и работа UI не требуют внешней сети.

README начинать с Compose-команды и адреса интерфейса, указать время
подготовки и способы диагностики: `docker compose ps`,
`docker compose logs -f app`; остановка — `docker compose down`.
Занятый порт 8080 должен давать понятную инструкцию, как его освободить
или изменить host-port в compose.yaml.

Прямой запуск оставить дополнительным способом для разработки:

```sh
uv sync --locked
npm --prefix web ci
npm --prefix web run build
uv run python run.py --data case/data --out out --serve
```

Без `--serve` команда должна закончить расчёт и выйти. С `--serve` — выполнить
расчёт, собрать готовые assets и данные в out, затем запустить сервер.
Добавить параметры `--host` и `--port`: локально по умолчанию
`127.0.0.1:8080`, в контейнере явно `0.0.0.0:8080`.
Отсутствующую сборку UI сообщать явно. Playwright и его браузеры —
dev-зависимости; для обычного запуска через Compose они не нужны.

Проверки, которые имеют смысл добавить при реализации:

- Синтетические маленькие графы: изолят, веер, сборщик, транзит,
  seed с неизвестным входом, depth=4 без выхода, встречные рёбра и петля.
- Несогласованные суммы/количества и отсутствующие концы рёбер приводят
  к явной ошибке, а не частично успешному результату.
- Реальный датасет: покрытие всех gid, контракт CSV/JSON, диапазоны,
  согласованность кластеров/рангов, объяснения и запрет NaN/Infinity в JSON.
- Повторный запуск с тем же окружением/config даёт те же роли, кластеры
  и порядок топа. Из сравнения исключить служебные длительности запуска.
- Время расчёта замерить отдельно от установки и сборки; цель < 5 минут.
- Проверить `docker compose config` и запуск из свежей копии без локальных
  .venv, node_modules, dist и out. Одной Compose-команды достаточно для
  healthy-сервиса на localhost:8080, рабочего поиска и скачивания CSV.
- Проверить остановку/повторный запуск, пересоздание контейнера и ошибку
  расчёта: отсутствует выдача устаревших результатов как успешных.
- `tsc` и production build; Playwright: поиск реального gid, выбор строки,
  соответствие карточки JSON, изолят, неизвестный gid, сброс фильтров,
  ошибка загрузки, отсутствие внешних запросов в offline-сценарии.

## 7. Задание агенту

Передать агенту этот файл, `PLAN.md`, инструкции AGENTS.md и весь `case/`.
Формулировка:

> Реализуй MVP по TECH_HANDOFF.md и исходному PDF. Начни с запуска starter
> и профилирования данных, затем получи валидные выгрузки и подключи UI
> к единому analysis.json. Продолжай существующий пайплайн. Выбери и
> задокументируй пороги на основе распределений, без хардкода gid.
> Обязательно реализуй Dockerfile, compose.yaml и .dockerignore: после
> `docker compose up -d --build` проект сам рассчитывает данные и доступен
> на http://localhost:8080 без установки Python/Node.js на хосте. Добавь
> healthcheck и проверь запуск с --wait из свежей копии репозитория.
> Не добавляй обязательную LLM-зависимость. Проверь граничные случаи,
> воспроизводимость, локальный сценарий и время выполнения. Обнови README,
> подготовь диаграмму и воспроизводимые выгрузки для сдачи. Сохрани исходные
> материалы и пользовательские изменения. Коммить проверенные логические блоки
> по правилам AGENTS.md. В конце сообщи команды запуска, результаты проверок
> и оставшиеся ограничения.
